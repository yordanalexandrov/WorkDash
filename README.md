# WorkDash

Локално табло за GitHub pull request-и: всичко, което иска внимание от мен, на един екран, с desktop
нотификации при важни промени.

- PR-и от няколко repo-та, групирани по действие: **Чака теб**, **Свободни за review**, **Готови за merge**, **Чакат други**, **Екипът**.
- CI, review-та, непрочетени коментари, конфликти и Jira линкове на всеки ред.
- Нотификации само за важното, по правила от конфигурацията.
- Хоства се локално с Docker.

> Статус: по една карта за всяко repo, а в нея PR-ите са разделени по секции. На всеки ред има CI, review-та, mergeability (conflict, needs rebase, blocked),
> draft, възраст и баджове с Jira тикетите. Непрочетените коментари и нотификациите предстоят. Виж [docs/plan.md](docs/plan.md).

Чии PR-и влизат в „Свободни за review“ и „Екипът“, се определя от `team`. Когато repo-то не изисква review
и GitHub не дава решение, PR-ът се смята за одобрен при `review.required_approvals` одобрения (по подразбиране 1).

Jira ключовете (`ABC-123`) се вадят от branch-а, заглавието и описанието на PR-а и стават линкове към
`jira.base_url` + ключа. С `jira.project_keys` остават само ключовете на тези проекти. Без `jira.base_url`
баджове няма. Към Jira не се правят заявки.
PR, който изчезне от отворените, се проверява еднократно по номер и се показва в „Наскоро затворени“ като merged или
closed за `review.recently_closed_window` (по подразбиране 24h). За него не се праща нотификация.

Issue таблото (превключвателят „PR-и / Issues“ или `i`) показва отворените issues на едно repo по **етапи**:
„Без етап“ отпред, после етапните етикети от `issues.columns` (или от `issues.repos.<owner/name>.columns` за repo
със собствен списък) по реда им, а отзад „Затворени“: затворените в рамките на `review.recently_closed_window`, като завършени или
„не е планиран“. Issue с няколко етапни етикета е в последния. Issues на repo се теглят, когато
таблото или табът на repo-то се отвори, най-често веднъж на минута; „Обнови“ (`r`) тегли веднага.

Всичко по-долу се задава от екрана „Настройки“ (⚙ в горната лента); имената в скоби са ключовете в `config.yaml`.

Нотификациите се включват и изключват по тип с `notifications.<тип>` (по подразбиране всички са включени).
Изключеното събитие се записва, но никога не се показва. В `notifications.quiet_hours` (например `"19:00-09:00"`,
може и през полунощ) събитията се записват без нотификация. Часът се чете в зоната от `TZ`; без нея е местното
време на машината, а в контейнера то е UTC, затова сложи например `TZ=America/New_York` в `.env`. Събитията, които
не са показани, защото таблото е било затворено, браузърът не е разрешил нотификации или е било тихо време, се
пращат при следващото отваряне или в края на тихите часове като една обобщена нотификация „N пропуснати събития“ и
списък „Пропуснати“ в таблото (най-новите 50). Отворено в тихите часове, таблото показва списъка без нотификация.

## Настройки

Токенът, repo-тата, екипът, Jira, review правилата, нотификациите, poll интервалът и етапите на issues се задават от екрана
„Настройки“ (⚙ в горната лента, или `#settings` в адреса), без да се пипат файлове. Таблото тръгва и празно и
казва какво липсва.

- **Токен**: fine-grained PAT с достъп само за четене до следените repo-та (Pull requests, Contents/Metadata,
  Commit statuses, Checks). Ако организацията не позволява fine-grained токени, ползвай classic PAT с `repo`
  или `gh auth token`. Текущият потребител се определя от токена. Преди запис токенът се проверява в GitHub;
  невалиден не се записва. Към браузъра не се връща, вижда се само маскиран.
- **Repos и екипът**: при добавяне GitHub се пита дали repo-то съществува и токенът го вижда, и дали login-ът
  съществува. Отговорът е предупреждение до името, записът не се спира.
- **Етапи на issues**: подреден списък от етикети, общ за всички repo-та, и по желание собствен списък за repo.
  Подсказките идват от етикетите на repo-то в GitHub; етикет, който го няма там, само предупреждава.
- „Запази“ записва `config.yaml` наведнъж и промяната влиза в сила веднага. Ако файлът е променен на ръка след
  отварянето на екрана, записът се отказва и екранът предлага да го зареди наново.
- Ако GitHub откаже токена по време на работа, poll-ът спира до нов токен, а таблото показва къде да се смени.

Всичко, което приложението пази, е в една data директория (`DATA_DIR`, в Docker volume-а `workdash-data`):
`config.yaml` с настройките, `github-token` (файл само за собственика, mode `0600`) и `workdash.db`. Защо там, а не
до `docker-compose.yml`: [docs/adr/0001](docs/adr/0001-settings-and-token-live-in-the-data-directory.md).

В `.env` остават само неща на средата:

```sh
echo "TZ=America/New_York" >> .env    # зоната, в която се четат тихите часове
echo "GITHUB_TOKEN=..." >> .env       # по желание: токенът за първия старт, после се сменя от „Настройки“
```

`.env` не се commit-ва.

### Преминаване от `config.yaml` до `docker-compose.yml`

Досега настройките бяха в `config.yaml` до `docker-compose.yml`, а токенът в `.env`. При първия старт с празна data
директория сървърът ги взема сам: при `npm start` копира `./config.yaml` (или `CONFIG_PATH`) без
`github.token_env`, а токена взема от променливата, която `token_env` е посочвал (по подразбиране `GITHUB_TOKEN`).
След това тези файлове не се четат.

Docker контейнерът вече не вижда директорията на проекта, затова там токенът идва от `.env` при първия старт, а
настройките се копират веднъж на ръка (махни реда `token_env` преди това, новата схема не го приема):

```sh
docker compose up -d --build
docker compose cp ./config.yaml workdash:/app/data/config.yaml
```

## Пускане

```sh
docker compose up -d --build
```

Таблото е на <http://localhost:3000>. Сървърът пита GitHub на всеки `github.poll_interval` и праща
резултата на отворените табла през SSE (`/api/events`), без reload. Превключвателят „При поискване“ в горната
лента спира периодичния poll: тогава сървърът пита GitHub само когато таблото се отвори или получи фокус (не по-често
от веднъж на 30s) и при „Обнови“ (`r`). Нотификациите идват с този poll, а повече от три наведнъж идват като едно обобщение.
Режимът е общ за всички отворени табла и остава след рестарт. Ако poll-ът се провали (невалиден
токен, rate limit, недостъпен GitHub), таблото показва причината, а последните успешни данни остават.
Последният snapshot се пази в SQLite във volume `workdash-data`, затова след рестарт таблото показва
запазените данни още преди първия нов poll.

Цена на един poll спрямо GitHub GraphQL rate limit-а (5000 точки на час):

- Списъкът с отворените PR-и (до 100 на repo, с проверките и review-тата) е една заявка за около 4 точки на repo.
- Коментарите, review threads и последните commit-и се дърпат само за нови PR-и и за PR-и с променен
  `updatedAt`, по 25 PR-а на заявка (1 точка за 1–3 PR-а, около 8 за 25). За непроменените се ползва записаното.
- При 4 repo-та и poll на всяка минута това са около 17–18 точки на poll, или към 1100 на час. Първият poll
  дърпа детайлите на всички PR-и наведнъж и струва повече (до около 130 точки за 400 PR-а).

Портът на хоста се сменя с `WORKDASH_PORT` в `.env`. Например за <http://dash>:

```sh
echo "WORKDASH_PORT=80" >> .env
echo "127.0.0.1 dash" | sudo tee -a /etc/hosts
```

Логове: `docker compose logs -f`. Промените в настройките се прилагат веднага, без рестарт: добавено repo
се появява на следващия poll, който тръгва веднага. `config.yaml` в data директорията може да се редактира и на
ръка (`docker compose exec workdash vi /app/data/config.yaml` или в `data/` без Docker); такава промяна се прилага
сама до секунда. Невалидна промяна се показва като грешка в таблото, а последната валидна конфигурация остава в сила.

### Инсталиране като приложение

В Chrome/Edge отвори таблото и избери „Install WorkDash“ (иконката в адресната лента или менюто ⋮ →
„Cast, save and share“ → „Install page as app“). Таблото се отваря в собствен прозорец с иконка.

Service worker-ът, а с него и инсталирането, изискват secure context. `localhost` е такъв, `http://dash`
не е. За `http://dash` пусни браузъра с `--unsafely-treat-insecure-origin-as-secure=http://dash` или
инсталирай от `http://localhost:<WORKDASH_PORT>`.

### Desktop app

```sh
npm install --prefix desktop   # веднъж: Electron и better-sqlite3 на desktop пакета
npm run desktop                # билдва web/dist и desktop/dist (main.cjs, preload.cjs) и пуска Electron
```

Сървърът върви в процеса на Electron на свободен порт на `127.0.0.1` (ADR 0002). Данните, размерът и позицията на
прозореца са в `~/.config/WorkDash`, а логът на сървъра е в `~/.config/WorkDash/logs/workdash.log` и започва
наново при всяко пускане. Токенът се въвежда от „Настройки“; env и стар `config.yaml` не се четат. С отключен OS
keyring токенът е криптиран в `github-token.enc`, без него е във файла `github-token` с mode `0600`, както при
`npm start`; стар `github-token` се мести в keyring-а, когато той се появи, а `github-token.enc`, който не се чете,
значи „няма токен“ и „Настройки“ го искат отново. Кой вариант е избран, пише в лога.

Затварянето на прозореца само го скрива: страницата продължава да проверява и да показва нативни нотификации, а
приложението спира от „Изход“ в tray-а. Повторно пускане показва вече отворения прозорец. Tray менюто има още:

- „Отвори“: показва прозореца (на Cinnamon и с клик върху иконата);
- „Пауза на нотификациите“: събитията чакат до изключване и идват като едно обобщение на пропуснатите, както след
  тихите часове; не се пази при рестарт;
- „Стартирай при вход“: пише или маха `~/.config/autostart/workdash.desktop`, който пуска `/usr/bin/workdash
  --hidden`, т.е. само инсталирания deb, скрит в tray-а.

Броят PR-и в „Чака теб“ е в tooltip-а на иконата, като червена точка върху нея и като число на иконата в Ubuntu Dock.

Ubuntu 24.04 и по-новите не позволяват на непривилегирован процес да прави user namespaces, затова sandbox-ът
на Chromium иска `chrome-sandbox` на root с mode `4755`. След всяко `npm install --prefix desktop`:

```sh
sudo chown root desktop/node_modules/electron/dist/chrome-sandbox
sudo chmod 4755 desktop/node_modules/electron/dist/chrome-sandbox
```

#### deb пакет

```sh
npm run build:deb                                    # desktop/release/workdash_<версия>_amd64.deb
sudo apt install ./desktop/release/workdash_*_amd64.deb
```

Пакетът (Ubuntu 22.04+, Linux Mint 21+, x64) слага приложението в `/opt/WorkDash`, команда `workdash` в `/usr/bin`,
запис в менюто с приложения и иконите от `desktop/build/icons` в `hicolor`. На Ubuntu 24.04 инсталира и AppArmor
профил, който позволява user namespaces на `/opt/WorkDash/workdash`, така че sandbox-ът работи без горните
`chown`/`chmod`. Dock-ът и Alt+Tab взимат иконата от `workdash.desktop` по WM_CLASS / app id `workdash`
(`desktopName` в `desktop/package.json`); `npm run desktop` получава същата икона, ако пакетът е инсталиран.
Без пакета `npm run desktop:dev-entry` пише `~/.local/share/applications/workdash-dev.desktop` със същия клас и
иконата от repo-то (и запис „WorkDash (dev)“ в менюто, който пуска вече билднатия `desktop/`);
`npm run desktop:dev-entry -- --remove` го маха, например след като инсталираш deb-а.

Версията на `desktop/` следва тази на корена. Release: `npm version <patch|minor|major>` вдига и двете, прави
commit и таг `v<версия>`; `git push --follow-tags` пуска `release.yml`, който прикача deb-а към draft Release.

## Разработка

```sh
npm install
npm test             # Vitest, и тестовете на desktop/
npm run typecheck    # иска npm install --prefix desktop (типовете на Electron)
npm run lint         # oxlint с типова информация (--type-aware); правилата са в .oxlintrc.json
npm run knip         # неизползвани файлове, export-и и зависимости
npm run guard        # няма ли служебни данни в repo-то (виж CLAUDE.md)
npm run build && node dist/main.js
npm run watch:web    # пресглобява web/dist/app.js при промяна в web/src
```

CI (`.github/workflows/ci.yml`) пуска typecheck, lint, тестовете и build на всеки PR и push в `main`
и проверява, че Docker образът се сглобява.
`.github/workflows/public.yml` пази публичното repo: `scripts/public-guard.ts` търси чужди имейли, Jira
инстанции и термини от частен списък във файловете, commit-ите и описанието на PR-а, а gitleaks търси
токени. Списъкът (истински имена, логини, Jira ключове) е в secret-а `PUBLIC_GUARD_DENYLIST`
на един ред, разделен със запетаи, за да го маскира логът цял, а локално в git-ignored файла `.public-guard-denylist`. CodeQL и Dependabot
са включени в настройките на repo-то и в `.github/dependabot.yml`.

Frontend-ът е Preact (TSX) в `web/src`, сглобен от esbuild в `web/dist`; статичните файлове са в `web/public`.

Без Docker приложението пази всичко в `data/` в текущата директория и слуша на `127.0.0.1:3000`. Директорията и
адресът се сменят с `DATA_DIR`, `HOST` и `PORT`; `CONFIG_PATH` е само старият `config.yaml` за първия старт.
API-то отговаря само под `localhost`, `127.0.0.1` и `[::1]`, а записващите заявки трябва да са JSON и от същия
origin, така че чужда страница в браузъра не може да смени токена или настройките.
